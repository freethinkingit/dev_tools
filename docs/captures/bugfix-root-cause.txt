  **Root cause.** The workflow rule's eval target grants no Bash: its Makefile line is only `--scaffold`. Since commit 1170121 on 2026-10-16, `bugfix` runs `gh issue view` while it loads, and `pr` has always run `git` and `gh` while it loads. In that sandbox each Skill call fails with "Permission to use Bash has been denied". The skill's text never reaches the session, and Claude improvises an answer.

  The routing graders still pass, because they see the Skill call itself. Only `states-symptom` looks for something the loaded skill would have said, so only it fails. Two consequences follow:

  - **The workflow eval proves less than it seems.** `pr-routes-to-pr-skill` passes 3 of 3 while the `pr` skill never loads in it.
  - **Real users are not affected.** The skills' `allowed-tools` pre-approve those commands outside the eval sandbox. This session's own `bugfix` load is the evidence.

  Inferred, not observed: that `states-symptom` passed before 1170121. No results from before 2026-10-16 remain on disk.

  **The fix I'd make.**

  - **Give the workflow target what the loaded skills need.** That is `--allow-tools Bash` with the `bin` wrappers first on the PATH, as every other target whose skills run git does. The two routing cases also get a scaffold that writes the wrappers.
  - **Add the regression guard.** It is a grader on `pr-routes-to-pr-skill` that fails when the trace holds "Shell command permission check failed". `bug-routes-to-bugfix` gets the same grader, so a skill that cannot load fails loudly instead of passing on the call alone.
