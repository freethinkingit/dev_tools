# Lenses

The review skill reads this file and launches one `review-arm` per `##` section below, all at once, and sends each arm the shared standard, the three sentences of this paragraph from "Across every lens" to its end, together with that arm's own `##` section as the lens, so the standard reaches every arm once and no section repeats it. A section added here is an arm added, a section removed is an arm removed, and a section reworded changes what that arm looks for; the skill's steps stay as they are. Each lens names the categories its findings carry, from the arm block's list. Across every lens, a finding worth reporting is one a competent senior reviewer would expect the author to address before merge: true and verifiable against the code at head, a real concern that would improve the change, and specific enough to act on. A finding not worth reporting is an incorrect or unverifiable claim, a duplicate, a style nit below the project's bar, or advice that would not improve the change or would make it worse. A pre-existing problem in a touched file counts when it is verifiable.

## correctness

This lens looks for code that does the wrong thing: logic errors, wrong conditions and comparisons, off-by-one bounds, wrong computations, values used before they are set or after they change, mishandled `None`, empty and boundary inputs, and behaviour that contradicts what the title, the body, a docstring or the surrounding code says it should do. It carries the category `correctness`, where most of a review's real findings sit. A true positive names the input or state that produces the wrong result, traces it through the code at head and says what the code does instead, and when the code can be run on its own, runs it on that input and quotes the result; The commonest wrong finding overlooks an existing guard or rests on a premise the code does not bear out, so the arm checks for a guard, a caller's precondition or a type that already rules the case out before reporting. A false positive asserts a bug the code already prevents, guesses at a caller's behaviour without reading it, or proposes a simplification that changes the behaviour or data shape downstream code reads. Error handling, concurrency, resource use and speed belong to the reliability lens; a swallowed exception that makes a function return a wrong result sits on the boundary, and this lens reports it only when the wrong result is the point.

## reliability

This lens looks for code that fails badly or slowly: errors that are swallowed, masked or reported as success, missing handling for a call that can fail, retries and timeouts that are missing or unbounded, races and shared state under concurrency, resources that are not released, faults that cascade instead of degrading, configuration defaults that can silently pick the wrong environment or provider, and dependency, build and CI changes that break or weaken the pipeline. It also looks at performance: unnecessary work in a loop, N+1 queries, inefficient algorithms on inputs that grow, unbounded memory and leaks. It carries the categories `reliability` and `performance`. A true positive names the failure or the load that triggers it, the path through the code and what the user or operator sees, such as a reported success for an operation that did not happen; a performance finding names the input size or call pattern that makes the cost real; when a failure path can be run on its own, the finding runs it and quotes what happened. A false positive asks for error handling where the caller already handles it, flags a theoretical race on state that is never shared, or calls code slow without an input that makes it so. A wrong result on the happy path belongs to the correctness lens and an exploitable failure to the security lens.

## security

This lens looks for concrete, exploitable vulnerabilities, covering at least injection (SQL, shell, template and similar, where untrusted input reaches an interpreter by concatenation or formatting), authentication and authorisation (a missing check, a check on the wrong subject, a bypass path, broken access control), secrets in code (a credential, key or token written into the source, configuration or tests, with its actual value), unsafe deserialisation of input the user controls, and path traversal (a path built from input that can escape its intended directory); it also covers cryptographic misuse, data exposure and supply-chain risks. It carries the category `security`, the smallest share of a review and the highest bar, because a security finding that cannot be exploited here costs the reviewer more trust than any other kind. A true positive traces a specific data flow from the untrusted source to the dangerous sink in this code, or shows the bypass path, the secret's value or the deserialised input, and says what an attacker gains; when the code that builds the sink's input can be run on its own, the finding runs it on a crafted input and quotes the string that reaches the sink. A false positive restates a best practice without showing how it is exploited here, such as boilerplate sanitisation advice, a generic warning to pin an action to a SHA or a mutable-tag alert, even when it names the variable or the action; it also includes a flow whose input is not in fact user-controlled or is already validated. A bug with no attacker in it belongs to the correctness or reliability lens.

## maintainability

This lens looks for what makes the change harder to read, change or use than it needs to be: names and structure that contradict the conventions of the surrounding code, duplicated domain logic that will drift, needless complexity, dead code, and misleading or redundant patterns; comments, docstrings, README and API docs that are stale, misleading, missing where a public contract needs them, or that describe the algorithm instead of the intent; API contracts, function signatures, type design and module boundaries that are awkward, leaky or inconsistent with the rest of the codebase; and user interfaces that shut out users, through missing accessibility, hard-coded text that defeats internationalisation, or unprofessional wording. It carries the categories `maintainability`, `documentation`, `api-architecture` and `accessibility`, the readability and usability side of a review. A true positive points at the specific code and the local convention, the stale sentence or the interface it is inconsistent with, and says what the reader or caller gets wrong because of it; a small finding is still a true positive when it names a concrete inconsistency, a typo in a public name or a reader-facing confusion, and is then low severity. A false positive is a personal preference with no local convention behind it, a comment that could be pasted onto any codebase unchanged, or a refactor that would not make this change better. Anything that changes behaviour belongs to the correctness, reliability or security lens.

## testing

This lens looks at the tests the change adds or should have added: behaviour the change introduces or alters with no test that would fail if it broke, missing boundary and error cases for new code paths, tests that assert the wrong thing or nothing, tests that restate an implementation constant or check their own input, fakes that do not enforce the real contract, flaky tests that depend on time, order or the network, and validation logic in the tests themselves. It carries the category `testing`. A true positive names the code path or case that is untested or wrongly tested and the test that would cover it, in the project's own test framework and style. A false positive asks for coverage of code that an existing test already covers, demands tests for trivial code the project does not test, or proposes a test that would not catch a real regression. A defect in the production code itself belongs to the lens that covers that kind of defect; this lens reports that the tests miss it.
